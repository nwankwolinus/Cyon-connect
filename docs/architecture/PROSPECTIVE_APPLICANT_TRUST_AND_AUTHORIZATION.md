# Prospective Applicant Trust and Authorization Design

## 1. Purpose and status

This document proposes the trust and authorization design needed before membership-application submission can be implemented. It supplements [the membership application data model](MEMBERSHIP_APPLICATION_DATA_MODEL.md), [the lifecycle contract](../planning/MEMBERSHIP_LIFECYCLE_CONTRACT_SPEC.md), and the owner-approved development-planning decisions recorded in [the lifecycle decision resolution](../planning/MEMBERSHIP_LIFECYCLE_DECISION_RESOLUTION.md) and [owner approval](../planning/MEMBERSHIP_LIFECYCLE_OWNER_APPROVAL.md).

This is technical design, not runtime behavior or a physical schema. Permission identifiers and data representations below are proposed, not implemented. The four decisions in Section 3 are approved development-planning decisions based on the Project Owner's explicit instruction in the project conversation on 7 November 2026. That instruction is the approval source; this document does not claim a signature, meeting, resolution, or separate external evidence. Approval does not prove deployment configuration, delivery infrastructure, reviewer appointments, or implementation. No applicant flow is ready to accept personal data until the prerequisites in Section 10 are met.

## 2. Verified repository baseline

- `supabase/migrations/20261008090000_identity_foundation.sql` defines `public.org_units`, `public.members`, and `public.user_accounts`. A member has one parish home-unit and status; `user_accounts` links an Auth identity to a member. The migration deliberately contains no member PII, membership applications, application decisions, or reviewer permissions.
- The identity migration seeds one parish row, but that seed does not establish that a prospective applicant belongs to that parish. The model has no applicant-to-parish relationship.
- The identity application flow obtains the caller through the cookie-aware server Supabase client and looks up the linked account/member (`modules/identity/infrastructure/supabase-trusted-authenticated-user.ts`, `modules/identity/infrastructure/supabase-identity-context-reader.ts`, `app/api/identity/me/route.ts`). It is a current-member identity flow and cannot establish prospective-applicant ownership before an account/member exists.
- `app/api/authorization/me/route.ts` and `modules/authorization` expose only the current caller's platform-administrator check. `supabase/migrations/20261014090000_platform_admin_bootstrap.sql` defines platform authorization only. It contains no membership-review permissions or reviewer-scope assignments.
- `infrastructure/supabase/server.ts` creates the cookie-aware authenticated server client. `infrastructure/supabase/admin.ts` uses a service-role key; service-role access bypasses ordinary RLS and is not proof of caller authority.
- The inspected presentation code implements password sign-in. No prospective-applicant sign-up, email/phone verification, recovery, application storage, screening, or membership-review flow was found. No mail/SMS delivery integration or application-level rate limiter was found in the inspected paths. Supabase project Auth settings and provider configuration were not inspected and are not established by repository code.
- The FRS v1.0 candidate lists member-profile attributes under `FR-MEM-006` but does not classify them for initial application. The Project Owner has since approved field-by-field initial-application requiredness and conditional details as MLD-16; the complete inventory is in `docs/planning/MEMBERSHIP_LIFECYCLE_CONTRACT_SPEC.md` §5.1. `FR-MEM-001`, `FR-MEM-011`, `FR-MEM-012`, `FR-SEC-002`, `FR-SEC-008`, and `FR-SEC-010` concern digital applications, duplicate routing, personal-data access controls, explicit authorization, backend enforcement, and least privilege. Applicant self-access, pre-review editing, trusted scope, scoped reviewer permissions, persisted screening, and idempotency remain controls to implement and verify.

## 3. Prospective applicant ownership

### Approved planning decisions — 7 November 2026

The Project Owner explicitly approved the following development-planning decisions in the project conversation. They are decisions, not implementation evidence:

1. Use a server-configured, single-parish intake destination. This selects the responsible intake/review destination and does not prove that an applicant belongs to the parish.
2. Use a minimum-field approach grounded in the actual FRS and limited to data necessary for application review. This does not make every `FR-MEM-006` profile field mandatory.
3. Require a designated grant authority and auditable reviewer-permission assignments. The authority's identity is not specified here and must not be inferred from another role.
4. Use evidence-based human duplicate review. A possible match or insufficient evidence remains unresolved and blocks final approval and member creation.

The recommended technical mechanisms that follow implement these boundaries; they do not expand them. MLD-16 requiredness/conditional field decisions are approved; field representation and privacy/access controls remain to be designed. External Auth configuration, the named reviewer-grant authority, permitted screening evidence, and runtime controls remain to be verified or specified before implementation.

The current product deployment is **single-parish: SS Joachim and Anne Catholic Church, Ijegun**. All current application intake, review, and parish operations must resolve to that parish. Keep the existing organization identifiers and useful parent relationships, but do not build multi-parish onboarding, tenant administration, cross-parish workflows, or generalized multi-tenant features for this release. Future extensibility is limited to preserving sound identifiers and scope boundaries.

### Options

| Approach                                                    | Advantages                                                                                                                                                                                                                 | Risks and missing capabilities                                                                                                                                                                                                                                                   |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prospective applicant has a separate Supabase Auth identity | Uses the repository's existing Auth session boundary; gives a stable Auth principal for ownership; applicant need not have `user_accounts` or `members`; ordinary session and password recovery can protect repeat access. | Current UI only signs in existing provisioned identities. Signup, verified-email requirements, applicant lifecycle, recovery UX, abuse controls, and Auth delivery configuration are not implemented or verified. Email verification proves mailbox control, not civil identity. |
| Email/phone challenge per application                       | Avoids a permanent password account and can prove current control of a channel.                                                                                                                                            | Delivery provider, challenge storage, rate limits, expiry, one-time consumption, recovery, and replay protection are absent. A channel challenge is not identity proof and may create a bearer-link risk. Phone delivery is not evidenced.                                       |
| Random application-access credential                        | Can grant narrowly scoped access without creating a member/account.                                                                                                                                                        | Requires high-entropy generation, hashed storage, expiry/rotation, single-use recovery, replay protection, secure delivery, and leakage-resistant URLs. No such credential system exists; bearer theft gives access.                                                             |
| Hybrid Auth account plus channel verification               | Stronger recovery and stable ownership when both are implemented correctly.                                                                                                                                                | Adds enrollment and delivery complexity; verification can still prove control rather than personhood. None is present now.                                                                                                                                                       |

### Recommendation: separate prospective-applicant Auth principal

Use a dedicated, authenticated prospective-applicant identity as the owner key. Require a verified email before an application is accepted. Bind the application to the Auth principal obtained from the trusted server session (`auth.uid()`/verified server-side `getUser()`), never to a caller-supplied Auth UUID. Do not require or create `public.user_accounts` or `public.members` for submission. The applicant may read only their own application and edit it only before review, with every operation rechecking ownership and state.

Use the existing Supabase Auth session and its configured recovery flow; do not add a separate application bearer token. Avoid exposing application identifiers as credentials. Return generic responses for unauthenticated or inaccessible records so callers cannot enumerate applications. Use verified contact data only for account ownership/contact; do not imply that it verifies the applicant's legal identity. A verified email change must follow the Auth provider's re-verification behavior and must not transfer application ownership to another principal.

The design must fail closed when the Auth principal is absent, email is unverified, session validity cannot be established, or the app cannot establish ownership. Never fall back to the identity `me` endpoint, client-supplied email, phone, or an application UUID as proof. Recovery remains Auth-provider mediated; lost access must not be resolved by changing the owner UUID through an unaudited support path.

The application should retain the verified Auth principal as its applicant owner. Do not create a `user_accounts` row or member association at signup/submission. After approval, member creation and the separate account-activation workflow may reference that same Auth principal only through their own approved, protected operations; they must revalidate identity and eligibility and must not infer a member link from the application owner field alone.

### Required operational prerequisites

Before server-side applicant-data intake, verify and configure prospective-applicant signup, email confirmation, session behavior, and recovery for the intended environment. Confirm a supported email delivery method and test delivery without using production applicants. Configure and verify abuse/rate protections at both Auth and application ingress; the repository currently supplies no application rate limiter. Prevent repeated submissions and verification-message abuse, apply generic responses, and avoid logging email, tokens, or submitted fields. The accepted Stage 2 form keeps entries in temporary client-side memory; until these environment and privacy capabilities are established, do not submit/persist applicant PII on the server or expose it to reviewers.

## 4. Trusted parish assignment

### Options

- **Server-configured single-parish intake:** suitable for the currently modeled single-parish deployment. The server assigns every new application to one configured intake parish after validating that the exact configured unit exists and has type `parish`. The setting is deployment-controlled, never request-controlled. It represents the parish responsible for receiving/reviewing the application; it does not establish the applicant's residence, membership, or belonging.
- **Scope-bearing invitation:** can associate entry with a parish, but requires an authorized invitation issuer, signed/unguessable expiring token, one-time consumption, revocation, and leakage controls. No invitation mechanism exists.
- **Applicant-selected parish:** not acceptable as evidence of authority or scope. It could be collected as a claim only if a separate requirement permits it; it must not drive reviewer authorization.
- **Existing member/account relationship:** unavailable for a prospective applicant by definition and must not be fabricated to obtain scope.

### Recommendation: configured intake scope

For a single-parish launch, derive `application_scope_org_unit_id` from a server-only deployment setting, validate it against `public.org_units` as a parish in the protected persistence operation, and persist the resolved scope with the application. Reject missing, malformed, nonexistent, non-parish, or ambiguous configuration. Never accept a client parish ID as authority. Changes to the configured intake parish require a controlled deployment/configuration change and must not silently rewrite existing application scope.

This is the narrowest practical server-established scope and supports later multi-parish expansion to an explicitly authorized invitation or assignment mechanism. The repository's seeded parish is reference data only and must not become an implicit default.

**Owner decision recorded:** the only operational parish for this release is SS Joachim and Anne Catholic Church, Ijegun. The server-configured parish is the application's intake/review destination, not a claim about applicant belonging. Configuration must resolve to the actual parish row for this named parish and must be validated server-side; applicants cannot select scope. No trusted applicant-to-parish belonging relationship exists before membership; this decision does not create one. Future multi-parish behavior requires separate approval.

Applicant-initiated parish changes are not permitted after submission. A correction, if needed, must be a separately authorized, attributable operation that revalidates the destination and preserves history. Current cross-parish review and operations are out of scope and denied; future multi-parish behavior requires separate approval.

## 5. Reviewer authorization and scope

### Proposed permission catalog

These identifiers are design proposals only; no corresponding membership authorization catalog or assignments exist. Applicant self-service is enforced by ownership and state, not by granting a reviewer role to applicants.

| Proposed permission                        | Effect                                                                  | Proposed scope                                                        |
| ------------------------------------------ | ----------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `membership.application.read`              | Read application fields needed for authorized review                    | Explicit parish assignment; default deny                              |
| `membership.application.decide`            | Record routine approval/rejection decision                              | Explicit parish assignment and valid current state                    |
| `membership.application.screening.resolve` | Record a screening disposition and minimal rationale/evidence reference | Explicit parish assignment; no automatic linking or identity mutation |
| `membership.application.escalated_decide`  | Final decision on escalated/disputed cases                              | Explicitly assigned scope; require escalation reason/current state    |
| `membership.application.audit.read`        | Read relevant security audit events, read-only                          | Independently assigned scope; no broad audit access by title          |

Proposed policy mapping: Secretary receives only routine review/read/decision capabilities within assigned parish scope. President oversight does not imply universal routine access; the President's final escalated/disputed authority is enforced through the separate escalated decision capability and explicit scope. Duplicate resolution is a distinct screening permission. Other executives receive nothing by virtue of title. `PLATFORM_ADMIN` receives none of these permissions by virtue of that role. Cross-parish access is denied by default.

Represent effective authority as explicit action grants associated with a reviewer principal and organizational unit, with grant/revocation attribution and effective status. The precise schema and administrator of those grants are not implemented. A protected server/database operation must derive the reviewer Auth principal from the session, verify active grant and scope, check application scope and current state, and only then return PII or mutate state. Never trust client-supplied actor, permission, role, scope, or application state. Role labels may inform governance but are not authorization evidence.

**Assignment governance prerequisite:** the repository defines no membership-review assignment workflow or policy identifying who may create/revoke those grants. Use a separately authorized, attributable provisioning process with default deny; do not grant permissions automatically from `PLATFORM_ADMIN` or self-service. The owner must designate the accountable authority and evidence required for reviewer appointment before reviewer endpoints or data access are enabled.

Revocation must take effect at the protected boundary on the next operation; cached permission decisions must not outlive the approved revocation behavior. Audit reads must be independently authorized and read-only. Applicant PII and match evidence are not available merely because a user can read security audit events.

## 6. Application, screening, and routing representation

The conceptual model should use a durable application record separate from `members` and `user_accounts`, keyed to the verified prospective-applicant Auth principal and a server-derived intake parish. Keep applicant submission data in a tightly protected application-owned representation; do not add PII to the identity tables or copy it into general audit events. Capture the owner-approved MLD-16 field set and classifications in `docs/planning/MEMBERSHIP_LIFECYCLE_CONTRACT_SPEC.md` §5.1; do not reduce the form to name and account email or reclassify approved fields. Use the verified Auth email without unnecessary duplicate entry or an independent editable email by default. Technical representation, validation beyond the approved details, privacy/access and retention controls remain prerequisites before storage.

Use the already approved conceptual screening outcomes: `no_apparent_match`, `possible_match`, `confirmed_existing_member_match`, and `insufficient_evidence`. Keep them distinct from application outcome and reviewer assignment. The application record is authoritative for current application outcome, paired with attributable business review-history records; state changes and history append occur atomically. Security audit is a separate accountability record.

Initial handling must not claim operational duplicate screening: `members` contains no applicant-comparable profile fields, and there is no approved matching algorithm or external identity source. The safe initial screening disposition is `insufficient_evidence` / unresolved and therefore blocks final approval, association, and member creation. `no_apparent_match` or `confirmed_existing_member_match` may be recorded only by a protected, explicitly authorized screening operation using approved evidence. Similarity alone is never proof. Do not return candidate-member information to applicants.

Maintain an explicit reviewer routing state/assignment independently of screening outcome. At minimum, unresolved/insufficient cases route to a scoped authorized review queue; no reviewer assignment or permission means the case stays unavailable for decision. Do not invent a physical state vocabulary as if approved. Applicants see only their submitted fields and a neutral status appropriate to their own application; screening evidence, candidate details, reviewer notes, and security audit remain reviewer-only under explicit scope.

Applicant edits are accepted only before the first review action and through a protected operation. An edit that affects screening invalidates the prior screening result to unresolved/insufficient and requires screening again; it never clears review history or grants access to prior match evidence. Use a row lock or version/compare-and-set at the database boundary to reject stale concurrent edits/reviews. Current outcome, screening disposition, routing, review event, and required audit write must not diverge on failure.

For submission idempotency, bind an operation-scoped key to the authenticated applicant, operation, and canonical validated payload digest. Same key and payload resolves to the same owned application; same key with a different payload conflicts; uniqueness/transaction handling prevents concurrent duplicate insertions. Verify ownership before returning any stored result. Do not store a raw PII request solely for idempotency. Keep a stable retry mapping for the application's lifetime unless an approved retention policy requires a different lifecycle; do not invent an expiry that could create duplicate submissions after expiration. The retention/disposal policy remains an implementation prerequisite.

## 7. End-to-end conceptual flow

1. Applicant enters through the CYON Connect application. Server-controlled signup creates or authenticates a prospective-applicant Auth identity; email is verified before accepting an application. No member/account record is created.
2. The server obtains the verified Auth principal from the session and checks required authentication/verification. It resolves the parish intake destination from trusted server configuration, validates the parish record, and rejects an unresolved scope.
3. The server validates only approved applicant fields, derives a payload digest, and atomically creates the application, idempotency mapping, initial unresolved screening/routing information, and required audit evidence. Client-supplied actor, parish, screening, reviewer, member ID, or application outcome is ignored/rejected.
4. The applicant may retrieve only their own application and edit only before review. Every retry/read checks ownership before response. Responses and logs do not expose other applications, match candidates, tokens, or unnecessary PII.
5. Because no approved matching source exists in the current schema, screening begins unresolved/insufficient. A reviewer decision is unavailable until an explicit reviewer grant and parish scope exist. Cases cannot advance to final approval or member creation.
6. When a permitted screening operation and scoped reviewer assignment later exist, an authorized reviewer records evidence reference/rationale and a disposition. This alone does not authorize member creation; the separately defined approval/member-creation transaction must revalidate current state and screening disposition.
7. Final approval/member association or creation follows the separate approved lifecycle transaction. Account creation/activation remains a separate workflow; neither applicant Auth nor approval implicitly creates an active application account.

Failure at any trust boundary fails closed. Do not create partial applications, return false success, expose whether a member match exists, or mutate identity links to make the flow pass.

## 8. Trust boundaries and safeguards

- **Browser to server:** untrusted applicant payload. Validate server-side; derive identity and scope independently.
- **Supabase Auth:** authenticates the principal and verifies control of configured channel only. It does not establish CYON membership or legal identity.
- **Application service to database:** use the caller's authenticated server client and a narrow protected database operation where possible. Do not use service-role as a substitute for authorization. If a service-role operation is unavoidable, independently validate the session principal, ownership/permission, scope, current state and input at the server/database boundary.
- **Database:** constraints, uniqueness, locks, transaction atomicity, grants and RLS reinforce the protected workflow. RLS own-row identity policies do not authorize membership review. Database owners/project administrators remain within the trusted computing boundary and may alter functions or grants.
- **Email links and recovery:** treat tokens as credentials; do not log or expose them in analytics/referrer headers; rely on the configured Auth verification/recovery path, not an unverified address or custom long-lived application token.
- **Logging and audit:** never log passwords, OTPs, access/refresh tokens, verification links, submitted PII, raw idempotency payloads, or match evidence. Persist required successful business audit in the same transaction as the business mutation. Denied-attempt recording requires a separate reliable mechanism where a failed business transaction cannot retain its own audit insert; that mechanism is not present or demonstrated.

## 9. Alternatives rejected for the first slice

- Do not make `public.user_accounts` or `public.members` a prerequisite for an applicant: it reverses the approved lifecycle and would manufacture identity prematurely.
- Do not accept a client-supplied parish UUID: it is not proof of applicant affiliation or reviewer scope.
- Do not use the existing single seeded parish as an implicit default: seed data does not define intake policy.
- Do not expose all applications through service-role-backed routes or broaden own-row identity RLS.
- Do not create a reusable bearer application token as a shortcut while Auth ownership/recovery is being designed.
- Do not call an unreviewed similarity query a duplicate decision or claim a person-level uniqueness guarantee.

## 11. Implementation sequence and acceptance criteria

1. **Close remaining scope/data prerequisites:** carry forward MLD-16 field classifications and specify their privacy/access/retention controls; designate reviewer-grant authority; verify Auth confirmation/recovery/delivery/rate controls; and approve permitted duplicate evidence. The parish intake meaning is already approved; acceptance requires a validated deployment setting, not another policy confirmation.
2. **Design the physical persistence and access boundary:** application, protected applicant data, screening/routing, review history, permission/scope assignment, idempotency, audit, grants/RLS, and narrow operations. Acceptance: threat review confirms applicant can only access own data; reviewers need explicit action+scope; service-role direct paths do not bypass policy; DB constraints cover races.
3. **Implement prospective-applicant Auth/session and submission:** no `user_accounts` or `members` side effect; verified principal and server-derived scope; server validation; atomic idempotency and durable submission. Acceptance: same key/same payload is safe, mismatch conflicts, concurrent retries produce one application, owner isolation holds, and failed writes roll back.
4. **Implement applicant read/edit:** pre-review only, ownership checked on each operation, edits invalidate screening and preserve history. Acceptance: cross-owner access, stale session, post-review edit, stale update, and untrusted scope tests deny safely.
5. **Implement screening/reviewer routing only after evidence and grants exist:** action-specific authorization and parish scope enforced in DB/server; no match evidence leaks to applicant; unresolved blocks approval. Acceptance: role-only and cross-parish calls deny, all four approved outcome values behave safely, and review/current-state/history/audit writes are consistent.
6. **Separate later lifecycle work:** approval/member creation/account activation remain outside this submission slice. Acceptance: submission APIs cannot approve, create/associate members, create accounts, activate status, or grant any role.

Required verification includes unit validation and ownership tests, database transaction/uniqueness/RLS tests under `anon`, `authenticated`, and narrowly intended server paths, and disposable-environment Auth confirmation/recovery/delivery checks. No such applicant flow or tests exist yet.

## 12. Scope exclusions

This design does not authorize or implement membership approval/rejection, member creation/association, account creation/activation, identity merge/relink/transfer, platform-admin dashboard or grants, cross-parish review, external identity verification, applicant phone verification, or a generic IAM framework. It does not declare legal/privacy compliance or prove CYON policy authority beyond the recorded project-owner decision evidence.
