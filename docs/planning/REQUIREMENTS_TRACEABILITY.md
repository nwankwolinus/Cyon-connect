### S3D-05 direct Auth signup enforcement investigation

The route eligibility gate alone did not guard the public Auth API. Architecture B is now implemented locally: after eligibility succeeds, a server-only Admin adapter creates an email/password identity with email confirmation disabled and requests the existing signup confirmation flow. Duplicate-email retries attempt resend rather than creating a second identity. DOB and eligibility data are not passed to Auth. The route is fail-closed unless `APPLICANT_REGISTRATION_ENABLED=true` and `APP_ENV=development`; the flag defaults false. Local `supabase/config.toml` disables global signup while retaining the email provider and confirmation setting; no local Auth stack was started to exercise those settings. Earlier read-only hosted development Auth settings showed public signup enabled; no hosted setting was changed. The two earlier synthetic direct signup probes returned HTTP 400; provider error text was not retained and no independent user-list/database check established whether identities persisted. They do not verify age enforcement. Thus the hosted public signup bypass remains open/unverified until separately authorized configuration and direct endpoint testing are complete.

Architecture B is implemented locally using an Admin create-unconfirmed plus confirmation-resend flow; Supabase interactions in automated tests are mocked. The signed-attestation hook remains an alternative design only and is not configured. Keep applicant registration disabled until the hosted direct-signup restriction and the eligible confirmation flow are demonstrated. See [Stage 3 implementation plan](STAGE_3_APPLICATION_SUBMISSION_IMPLEMENTATION_PLAN.md) for the selected implementation, security limits, and verification steps.
