### Direct-signup age-policy investigation (2026-11-10)

#### Pre-implementation threat model and alternatives

At the time of the initial investigation, the registration composition called public `auth.signUp()` after its server-side DOB check. The browser's public Auth key allowed direct signup requests that bypassed this application route while provider signup was enabled. The development settings then reported `disable_signup=false`; local configuration also allowed signup. A repository search found no Admin identity-creation path. Subsequent implementation is recorded above and replaces that route.

The current implementation still follows these security boundaries: the applicant submits DOB to the same-origin server route; the server validates the 16–40 rule before any Admin call; the Admin adapter accepts only email/password and explicitly creates an unconfirmed identity; DOB and eligibility proof are absent from Auth attributes and metadata. The browser does not receive the privileged key. Email confirmation is requested through the Auth signup-resend path, and session verification continues to require `email_confirmed_at`.

Supabase documents a Before User Created Auth Hook (Free and Pro), implemented as an HTTP endpoint or Postgres function, which sees the pending user/request metadata and can reject creation. It does not receive trusted DOB unless sent as metadata, which is prohibited. A hook could validate server-signed evidence, but that would add token/metadata, replay, secret rotation, and hook-availability concerns. Project-specific hosted hook configuration has not been verified. Option C—public signup enabled with only the CYON route gate—does not prevent bypass and is rejected. The Project Owner approved Architecture B; the alternatives are retained as design history, not pending owner choices. Sources: [Before User Created Hook](https://supabase.com/docs/guides/auth/auth-hooks/before-user-created-hook), [Auth Hooks](https://supabase.com/docs/guides/auth/auth-hooks).

For Architecture B, the hosted development project must have global public signup disabled while the email provider remains enabled for existing sign-in and confirmation. The local configuration now expresses that boundary, but it has not been run against a local Auth server. Before enabling registration in any hosted environment, verify the provider setting and all alternate identity providers, exercise direct `/auth/v1/signup` and establish no identity was created, and verify eligible Admin creation plus confirmation delivery. The hosted Auth configuration has not been changed in this increment.

4. Test failure-closed behavior: missing/invalid/forged evidence or hook timeout (Architecture A), or disabled direct signup and unavailable/ambiguous Admin creation response (Architecture B), never produces a successful applicant session or false registration receipt.
5. Verify DOB is absent from Auth request attributes/metadata, provider logs exposed to parish roles, browser bundles, URLs, application logs, and audit events. Verify signing/Admin secrets remain server-only and rotate/recovery procedures are approved.
6. Complete the required S3D-05C KMS/security evidence before any DOB persistence/deployment. Do not enable live applicant registration while provider-level enforcement remains unverified.

## 4. Database and migration considerations

- No membership application table exists in the inspected local migration set. Stage 3 requires an additive schema; do not retrofit application meaning into `members` or `user_accounts`.
- The application owner should reference the verified Auth UUID, not an account UUID. Parish relationship must reference exactly the server-resolved `org_units` parish and preserve the typed organization relationship.
- The schema must store the entire accepted submitted application or protected snapshot, but the final representation (typed columns versus protected structured payload or multiple relations) follows field-level privacy/access decisions.
- Application state, screening outcome, and membership status are three different concepts. Do not add `rejected` to `members.membership_status`.
- The resubmission FK must not overwrite predecessor state/data/history; the database FK proves only record existence, so rejected status and owner linkage must be checked in the protected transaction.
- Idempotency unique constraints and transaction locking/version rules must handle concurrent calls. Do not impose person-level uniqueness based on PII.
- Enable RLS and explicitly review grants/policies. Authenticated direct DML should not bypass validated submission. Service-role bypass is not authorization; every caller needs independent server checks. No DML to member/account tables is required by this stage.
- Never run migrations against a linked or unverified project. Migration tooling needs a target assertion and a disposable development database; the local development URL guard does not constitute universal deployment protection.

## 5. Verification strategy

### Unit and contract

- Server payload schema covers every MLD-16 required, optional, and conditional field, including 52 directory choices plus optional Other text; no additional fields.
- Date validity/future-date, enum, contact/phone structure, conditional address/sacrament/parish/society validation, and unknown fields rejected.
- Idempotency digest canonicalization stable across equivalent normalized payloads; same key/different payload conflicts.
- Use cases derive Auth owner from trusted port, parish from trusted resolver, and reject unverified principal/config failures.

### Route/security

- Unauthenticated, expired, unverified, wrong-origin, malformed, oversized, or forged owner/parish/state requests create no record.
- Same-owner read only; cross-owner/guessed application IDs receive a non-enumerating response.
- Applicant cannot write screening, review outcome, member association, account association, role, or audit fields.
- `PLATFORM_ADMIN` only and executive title only do not authorize review. Missing/revoked/wrong-parish grant defaults deny.
- PII absent from URLs, response errors, structured logs, ordinary tracing, and analytics.

### Database/migration/concurrency

- Foreign keys/type checks, status/outcome constraints, idempotency uniqueness, predecessor semantics, RLS, grants, and no direct client writes tested under relevant roles.
- Concurrent identical requests result in one row set; mismatched reuse leaves original unchanged; stale version conflicts.
- Inject failures after each transaction write and confirm application, payload, idempotency, review history, and required successful audit all roll back.
- Simulate commit success with response loss and safe authorized retry.
- Assert no `members` or `user_accounts` mutation for any submission path.
- Test denied-event reliability separately; a rolled-back business transaction cannot preserve its own audit insert.

### Integration and rollout

- Use local test database first, then explicitly identified non-production security-test project only with owner approval and sanitized target verification. No production access.
- Use synthetic records only. Confirm operational parish UUID/name/type via approved safe evidence; do not assume the local seed or earlier UUID is current.
- Feature flag/route gate keeps intake disabled until privacy/access controls, reviewer disposition path, and required operational settings pass.
- Rollback/disable means stop new submission and preserve accepted application/history; do not delete data or reset a shared database. Schema rollback must account for submitted PII and audit/history retention before execution.

### Expired passport-photo cleanup worker (local implementation)

Migration `20261115100000_membership_application_photo_cleanup.sql` extends the existing `application_photos` queue with provenance, retry/backoff metadata, and a five-minute lease. A service-only claim RPC uses `FOR UPDATE SKIP LOCKED` and limits each batch to 10. Stale leases become claimable automatically. The worker validates the canonical object-key structure and expiry evidence, calls the private Supabase Storage API, then deletes queue metadata only after Storage confirms deletion or exact `NoSuchKey` absence. Transient failures are retried with exponential delay capped at six hours; malformed paths are blocked for operator review. If Storage succeeds but DB completion fails, the lease expires and another run safely retries deletion.

Scheduling uses `pg_cron` and `pg_net` every 15 minutes to invoke `/api/internal/membership-photo-cleanup`. The database HMAC-signs a timestamp/request-ID pair using `extensions.hmac`; after signature and timestamp verification, the server atomically consumes the request ID through a private service-only RPC. A separate 15-minute `pg_cron` job prunes expired replay IDs even when there are no valid invocations; accepted requests also opportunistically prune expired entries. The endpoint reads at most 1 KiB incrementally and cancels oversized streams. The worker uses server-only service-role credentials, caps individual network operations at 15 seconds, and aborts after three minutes—two minutes before the five-minute database lease expires. Storage fetches inherit cancellation signals. It performs at most 10 deletions with four concurrent Storage calls.

Before migration deployment, verify `pg_cron`, `pg_net` (`net.http_post(text,jsonb,jsonb,jsonb,integer)`), Vault, and `extensions.hmac(bytea,bytea,text)`. Store the HTTPS endpoint as Vault secret `membership_photo_cleanup_url`; store a random key of at least 32 bytes as `membership_photo_cleanup_hmac_secret` in Vault and the same value in server-only `MEMBERSHIP_PHOTO_CLEANUP_HMAC_SECRET`. Never expose the key to browser code or commit it. Restrict database access to `net.http_request_queue`, which temporarily contains signed requests. Do not enable the schedule until the deployed endpoint and both secrets are ready.

Successful object deletion writes a payload-free `membership_application.photo_cleanup_completed` security-audit event; it contains no applicant ID, photo ID, object path, or image data. Operators with authorized database administration access can inspect queue counts without selecting applicant IDs or object paths:

```sql
select deletion_reason, deletion_last_failure, (deletion_blocked_at is not null) as blocked,
       count(*) as jobs, min(deletion_queued_at) as oldest_queued_at,
       min(deletion_next_attempt_at) as next_attempt_at
from membership_private.application_photos
where state = 'pending_delete'
group by deletion_reason, deletion_last_failure, deletion_blocked_at is not null
order by oldest_queued_at;
```

Also inspect recent `cron.job_run_details`, `net._http_response`, and server logs for the endpoint. To verify physical deletion, use a synthetic expired draft in the authorized non-production project, confirm its job completes, and confirm the object is absent through private Storage API/admin tooling; do not use public or signed image URLs. Replay protection requires applying `20261116100000_membership_photo_cleanup_replay_protection.sql` after the cleanup migration. This worker and schedule are implemented locally only. Hosted extensions, Vault configuration, delivery, migration deployment and Storage behavior remain unverified. Submitted-photo retention remains unresolved.
